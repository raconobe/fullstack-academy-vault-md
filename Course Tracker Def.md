In PHP CRUD applications, combining or handling both `$_GET` and `$_POST` variables is necessary because **GET** and **POST** serve distinct semantic purposes in web interactions. **GET** is typically used for **Read** operations (e.g., fetching a record by ID via URL query parameters like `?id=5`), while **POST** is used for **Create**, **Update**, and **Delete** operations (e.g., submitting form data to modify or insert records).

Developers often need to access both because a single script may handle multiple states, such as displaying an edit form (via `$_GET` to identify the record) and processing the submission (via `$_POST` to save changes). Alternatively, using `$_REQUEST` merges these arrays (along with cookies) into one, but this is generally discouraged due to security risks and ambiguity; instead, explicitly checking `isset($_GET['id'])` and `$_POST['data']` ensures clear separation of concerns and prevents conflicts where a variable name might exist in both arrays.



---

Yes, exactly. **GET parameters are visible in the URL**, which means:

- They appear in **browser history**, **server logs**, and can be **bookmarked/shared** accidentally.
- Anyone with access to the URL can see and **manipulate** the parameters (e.g., change `?id=3434` to `?id=1` to view someone else's record).
- They can be **replayed** simply by re-requesting the URL.

This is why the rule of thumb is:

| Method | Use for | Why |
|--------|---------|-----|
| **GET** | Read / filter / identify (e.g., `?id=5`) | The data is just an *identifier*, not sensitive |
| **POST** | Create, Update, Delete | The data is *state-changing* and should not be exposed in the URL |

**Key point:** GET isn't "insecure" for *identifiers* (like an ID), but it **is** insecure for **sensitive data** (passwords, tokens, personal info) or **destructive actions**. That's why:

- You'd use `GET` to *load* an edit form: `/edit.php?id=5`
- You'd use `POST` to *submit* the changes: `POST /update.php` with the form data in the body

Even so, **never trust `$_GET` values directly** — always validate and sanitize them (use prepared statements for SQL) to prevent **IDOR** (Insecure Direct Object Reference) and **SQL injection** attacks.



---


No, you **can't** (and shouldn't) use only GET for a full CRUD app. Here's why:

**GET is "safe" and "idempotent" by HTTP spec** — meaning it should never change server state. If you use GET for Create, Update, or Delete:

1. **Browsers and proxies will cache GET responses** — your "delete" might get served from cache and never actually run.
2. **Web crawlers, prefetchers, and link previewers** will hit your GET URLs and accidentally trigger destructive actions.
3. **The browser back button** will re-fire the GET request, potentially re-deleting or re-creating records.
4. **CSRF protection becomes meaningless** — CSRF tokens protect POST forms, not plain links.

So the practical split in a PHP CRUD app is:

| Operation | Method | Example |
|-----------|--------|---------|
| **R**ead (list) | GET | `GET index.php` |
| **R**ead (single) | GET | `GET view.php?id=5` |
| **C**reate | POST | `POST create.php` (form submit) |
| **U**pdate | POST | `POST update.php` (form submit) |
| **D**elete | POST | `POST delete.php` (form submit) |

You'll still use `$_GET['id']` to *identify* which record to load into the edit/delete form, but the actual **state-changing action** is always submitted via POST. That's why you see both in the same script.



---

Technically yes, it **will work** — PHP doesn't stop you. But you lose important things:

1. **No caching** — GET responses can be cached by browsers, proxies, and CDNs. POST responses cannot. Your list/view pages will hit the database every single time.
2. **No bookmarking/sharing** — a user can't save `?id=5` or share a link to a specific record.
3. **"Resubmit form" warning** — pressing the browser **back button** after a POST will show the annoying "Are you sure you want to resubmit?" dialog.
4. **Breaks HTTP semantics** — proxies, crawlers, and dev tools expect GET to be safe and cacheable. Using POST for reads confuses them.

So the practical answer:

- **For a small personal project** — sure, POST everything and it'll work fine.
- **For anything you want to scale, cache, or maintain** — use GET for Read, POST for Create/Update/Delete.

The "resubmit form" warning alone is annoying enough that most developers stick with the GET-for-reads pattern.

Not really. The raw speed difference between GET and POST is **negligible** — benchmarks show them performing almost identically for the same operation.

The real reasons to use GET for reads are:

1. **Caching** — this *is* a performance thing, but it's not that GET is "faster." It's that browsers/CDNs/proxies **cache GET responses** and skip the server entirely on repeat visits. POST is never cached, so every request hits your database.
2. **HTTP semantics** — GET is idempotent and "safe" by spec, which lets infrastructure (proxies, load balancers, CDNs) treat it differently and optimize it.
3. **Bookmarks/sharing** — not performance at all.

So it's **~20% caching benefit, ~80% correctness/semantics**. If you used POST for reads on a small app, it wouldn't be noticeably slower — you'd just lose caching and break conventions that infrastructure relies on.

Yes, it **will** be slower than a PHP `include`, but for a small CRUD app the difference is usually negligible. Here's what actually happens:

**What you lose vs. `include`:**

1. **Extra HTTP requests** — each `fetch('templates/header.html')` is a separate round-trip. If you call 5 templates sequentially (await one after another), you get a **request waterfall**: each one waits for the previous to finish.
2. **Slower first paint** — the browser shows a blank page until JS loads, executes, fetches templates, and injects them. With `include`, the HTML arrives in one response and renders immediately.
3. **No caching by default** — unless you set proper `Cache-Control` headers, the browser re-fetches those template files on every page load.

**When it's fine:**

- A handful of small templates (header, footer, a card) → the extra latency is maybe 50–200ms total. Not noticeable.
- You can mitigate by fetching all templates **in parallel** with `Promise.all` instead of sequentially.

**When it becomes a problem:**

- Many templates loaded sequentially → waterfall adds up.
- Templates are large or dynamic (require server processing) → each fetch hits the backend.
- SEO matters → crawlers may not execute JS, so they see an empty page.

**TL;DR:** For a small PHP CRUD app, just use `include` or `require`. It's one request, renders instantly, and you don't need to think about waterfalls or caching. Client-side template loading is useful for SPAs or when you need to swap content without a full page reload — not for initial page structure.

**Project structure:**
```
project/
├── index.php
├── view.php
├── create.php
├── update.php
├── delete.php
└── partials/
    ├── header.php
    ├── nav.php
    ├── footer.php
    └── form-field.php
```

**`partials/nav.php`:**
```html
<nav>
    <a href="index.php">Home</a>
    <a href="create.php">Add New</a>
    <?php if (isset($_SESSION['user'])): ?>
        <a href="logout.php">Logout</a>
    <?php endif; ?>
</nav>
```

**Any page (e.g. `index.php`):**
```php
<?php include __DIR__ . '/partials/header.php'; ?>
<?php include __DIR__ . '/partials/nav.php'; ?>

<!-- Your page-specific content here -->
<table>...</table>

<?php include __DIR__ . '/partials/footer.php'; ?>
```

**Why this is better than JS fetch for your use case:**

| | PHP `include` | JS `fetch` |
|---|---|---|
| Extra requests | 0 | 1 per template |
| First render | Instant | Wait for JS + fetch |
| SEO | Full HTML in source | Empty until JS runs |
| Complexity | One line | Promise, error handling, etc. |
| Performance | Negligible overhead | Waterfall risk |

**Tip for passing data to partials:**

```php
// partials/form-field.php
<label for="<?= $name ?>"><?= $label ?></label>
<input type="<?= $type ?? 'text' ?>" name="<?= $name ?>" id="<?= $name ?>" value="<?= htmlspecialchars($value ?? '') ?>">

// In your page:
$name  = 'title';
$label = 'Title';
$value = 'My Post';
include __DIR__ . '/partials/form-field.php';
```

Variables defined before the `include` are automatically available inside it — no need for JS, no extra requests, and your pages stay short and readable.

What you're describing is just **JS functions that return HTML**. That's it. No SSG, no framework, no build step.

```js
// components.js

function nav() {
  return `
    <nav>
      <a href="/">Home</a>
      <a href="/about">About</a>
      <a href="/contact">Contact</a>
    </nav>
  `;
}

function card(title, body) {
  return `
    <div class="card">
      <h3>${title}</h3>
      <p>${body}</p>
    </div>
  `;
}

function footer() {
  return `<footer>&copy; 2026</footer>`;
}
```

```html
<!-- index.html -->
<script src="components.js"></script>
<script>
  document.querySelector('#nav').innerHTML  = nav();
  document.querySelector('#cards').innerHTML = [
    card("First", "Some text"),
    card("Second", "Other text")
  ].join('');
  document.querySelector('#footer').innerHTML = footer();
</script>
```

That's literally your "function in Java" mental model. You define it once, call it anywhere, pass arguments, compose them.

**If you want it slightly more structured** (closer to a class), use **Web Components** — still no build step, no framework, just native browser:

```js
class MyNav extends HTMLElement {
  connectedCallback() {
    this.innerHTML = `
      <nav>
        <a href="/">Home</a>
        <a href="/about">About</a>
      </nav>
    `;
  }
}
customElements.define('my-nav', MyNav);
```

```html
<my-nav></my-nav>
```

**Comparison:**

| Approach | Build step? | Composable? | Like a function? |
|---|---|---|---|
| JS function returning HTML | No | Yes | ✅ Exactly |
| Web Components | No | Yes | ✅ + scoped styles |
| SSG | Yes | Yes | ❌ Overkill for you |

For your use case — small static sites, reusable snippets, no server — **plain JS functions** are the closest match to how you think. Web Components add the bonus of scoped CSS and clean HTML syntax (`<my-nav>` instead of a `<div id="nav">`), but they're optional.

**Static site:**
- `components.js` is loaded **once** and cached by the browser. After the first visit, it's served from cache (0ms network).
- Executing `nav()` or `card("title", "body")` is just a **string concatenation** — takes microseconds, not milliseconds.

**Comparison:**

| Approach | Extra latency |
|---|---|
| Inline HTML | 0 |
| JS function (cached) | ~0 (microseconds to execute) |
| JS `fetch` per template | 50–200ms per request |
| PHP `include` | 0 |

The JS function approach is basically identical to inline HTML in terms of latency. The only scenario where it'd be slightly slower is the **very first page load** before `components.js` is cached — and even then it's just one small file download, not a waterfall.

**File structure:**
```
static/
├── index.html
├── js/
│   ├── main.js
│   └── components/
│       ├── nav.js
│       ├── card.js
│       ├── footer.js
│       └── form-field.js
```

**`js/components/nav.js`:**
```js
export function nav() {
  return `
    <nav>
      <a href="/">Home</a>
      <a href="/about">About</a>
    </nav>
  `;
}
```

**`js/components/card.js`:**
```js
export function card(title, body) {
  return `
    <div class="card">
      <h3>${title}</h3>
      <p>${body}</p>
    </div>
  `;

```

**`js/main.js`:**
```js
import { nav } from './components/nav.js';
import { card } from './components/card.js';
import { footer } from './components/footer.js';

document.querySelector('#nav').innerHTML    = nav();
document.querySelector('#cards').innerHTML  = card("First", "Text");

```

```html
<script type="module" src="js/main.js"></script>
```

That's it. `import`/`export` is native ES6, no build step, no bundler. Each file stays small and focused.

```html
<script src="js/components/nav.js"></script>
<script src="js/components/card.js"></script>
<script src="js/main.js"></script>
```

And in each file, just define the function globally (no `export`):
```js
// nav.js
function nav() {
  return `<nav>...</nav>`;
}
```

**So your mental model maps directly:**

| PHP | JS (static) |
|---|---|
| `include 'nav.php'` | `import { nav } from './nav.js'` |
| One file per component | One file per component |
| Variables available in scope | Pass as arguments |

You'll never hit the "one giant file" problem because you split it the same way you'd split any Java/C project — one file per concern.

**"Template" approach (fetch):**
```html
<div id="nav"></div>
<script>
  fetch('templates/nav.html')       // ← HTTP request #2
    .then(r => r.text())
    .then(html => {
      document.querySelector('#nav').innerHTML = html;
    });
  fetch('templates/card.html')      // ← HTTP request #3
  fetch('templates/footer.html')    // ← HTTP request #4
</script>
```

Each `fetch` is a **new HTTP request**. That means:
- **Network round-trip** (DNS → TCP → TLS → HTTP → response): 50–200ms each on a decent connection, more on mobile.
- **Waterfall** if you `await` them sequentially: 3 templates = 150–600ms of *waiting for the network* before anything renders.
- **First paint is blank** until all fetches resolve and JS injects the HTML.

The browser can't render what it doesn't have yet.

---

**"JS functions + import" approach:**
```html
<script type="module" src="js/main.js"></script>
```

```js
// main.js — loaded ONCE with the page, then cached forever
import { nav } from './components/nav.js';
import { card } from './components/card.js';

document.querySelector('#nav').innerHTML = nav();
document.querySelector('#cards').innerHTML = card("Title", "Body");
```

What happens:
1. Browser loads the HTML → sees the `<script type="module">` tag.
2. Downloads `main.js` (one request, same as loading any CSS/JS).
3. The `import` statements pull in the other files — but the browser **resolves them in parallel** (not a waterfall), and they're **cached** after the first visit.
4. `nav()` executes → it's just a **string being concatenated in memory** → takes **microseconds** (0.001ms, not 50ms).
5. `.innerHTML = ...` → browser renders.

**Total extra cost: zero network requests after the initial page load. Execution time: negligible.**

## Why "REST across languages" works as a learning axis

REST is a **protocol-level** concept. The HTTP verbs, status codes, JSON structure, auth patterns — those are identical whether you implement them in Go, Node, PHP, or Java. So you learn the *concept* once and then each new language is just "how do I express this same thing here?"

That's much faster than learning each language in isolation and then wondering how they all connect.

## Suggested order (if you're starting fresh)

| Order | Language | Why |
|---|---|---|
| 1 | **Node/Express** | Fastest feedback loop, minimal boilerplate, huge tutorial ecosystem |
| 2 | **PHP (Laravel or Slim)** | You already know it, and it's the most "web-native" language |
| 3 | **Go (Gin or stdlib)** | Forces you to think about structure explicitly (no magic), great for understanding what the framework is hiding |
| 4 | **Java (Spring Boot)** | Most verbose, but the most transferable for job market; once you've done the others, Spring's conventions click fast |

Each one reinforces the same REST concepts while teaching you a different way to organize code.

## What to actually build each time

Don't just follow tutorials passively. Build the **same small API** in each language (e.g., a CRUD for "tasks" with auth):

- `GET /tasks`
- `POST /tasks`
- `GET /tasks/:id`
- `PUT /tasks/:id`
- `DELETE /tasks/:id`
- `POST /login` → returns a token
- Middleware that checks the token

After doing this in 3–4 languages, you'll see the patterns clearly and you'll have a reusable mental library (your "own libraries" point from earlier).

## One caveat

Don't try to learn all four *at the same time*. Go deep in one until you can build the CRUD from memory, then move to the next. Depth in 2 languages beats surface in 4.

Yes, you can compile a Node.js application into a standalone executable (`.exe`) to run a server without requiring Node.js to be installed on the target machine. This is achieved by bundling the Node.js runtime, your source code, and dependencies into a single binary file.

**Popular Tools and Methods:**

*   **Vercel/pkg:** A widely used command-line tool that compiles Node.js projects into executables. You can run `pkg server.js` to generate a `.exe` file that runs the server independently.
*   **Nexe:** Another robust option that creates a single executable out of your Node.js apps, supporting cross-platform builds and dynamic requires.
*   **Node.js Native SEA (Single Executable Applications):** Starting with Node.js 18.16.0, Node.js offers experimental native support for creating single executables. This often involves using a bundler like **esbuild** to combine dependencies and then using the `node --experimental-sea-config` command to embed the code into the Node binary.
*   **Bun:** The Bun runtime also provides a built-in `--compile` flag to package code into an executable.

**Key Benefits:**
*   **Portability:** The executable runs on systems without Node.js installed.
*   **Security:** Source code can be obfuscated or hidden within the binary.
*   **Distribution:** Simplifies deployment by providing a single file instead of a directory with `node_modules`.

**Example using pkg:**
```bash
npm install -g pkg
pkg server.js
```
This generates an executable (e.g., `server.exe` on Windows) that can be run directly to start your server.

Good question. The honest answer is: **there is no single dominant "Sass of HTML"**, and that's telling.

Here's why the analogy breaks down:

| Language | Pain point | Solution |
|---|---|---|
| **JS** | No types → bugs, no safety | **TypeScript** (adds an entire type system) |
| **CSS** | No variables, no nesting, no logic | **Sass** (adds features CSS lacked) |
| **HTML** | Verbosity (closing tags, quotes) | **Pug / HAML** (just removes boilerplate) |

HTML's problem is **cosmetic**, not structural. There's no "missing feature" like types or variables — just repetition. That's why no HTML preprocessor ever hit the same adoption as TypeScript or Sass. The pain isn't bad enough to justify learning a new syntax.

**What actually "won" for HTML:**

- **Frameworks** (React, Vue, Svelte, Astro) — they sidestep the problem entirely by giving you JSX/Svelte/Astro templates
- **Web Components** (`<template>`, `<slot>`) — native browser modularity, no build step
- **Just writing less HTML** — modern CSS + semantic tags mean fewer lines overall

So the ecosystem kind of decided: *"HTML is simple enough, just use a framework or Web Components."*

If you want the closest thing to a "Sass for HTML" that stays **HTML-first** (not a framework), it's still **Pug** or **EJS** — but they're tools, not a revolution. No one's going to say "I use Pug" the same way people say "I use TypeScript."

## Simulating `include` with plain JS

The simplest "include" — just fetch a partial and paste it where you want it:

```html
<!-- index.html -->
<!DOCTYPE html>
<html>
<head>
  <title>My Page</title>
  <link rel="stylesheet" href="style.css">
</head>
<body>

  <!-- This placeholder gets replaced with the partial's content -->
  <div data-include="partials/header.html"></div>

  <main>
    <h1>Hello</h1>
    <p>Just normal HTML.</p>
  </main>

  <div data-include="partials/footer.html"></div>

</body>
</html>
```

// include.js
async function loadIncludes() {

  for (const el of elements) {
    const path = el.getAttribute('data-include');
    const response = await fetch(path);
    const html = await response.text();
    el.outerHTML = html; // replace the <div data-include> with the fetched content
  }
}

loadIncludes();
```

Let me break it down step by step:

**1. What the browser sees FIRST (before JS runs):**

```html
<div data-include="partials/header.html"></div>
```

That's just an **empty `<div>`** with a custom attribute `data-include`. The browser doesn't know what to do with it — it's just a placeholder. You'd see a blank space.

**2. What the JS does (after the page loads):**

```js
const el = document.querySelector('[data-include="partials/header.html"]');
// → grabs that empty <div>

const html = await fetch('partials/header.html').then(r => r.text());
// → downloads the file "partials/header.html" from your server
//   and gets its text content: "<header><nav>...</nav></header>"

el.outerHTML = html;
// → REPLACES the empty <div> with the fetched HTML
```

**3. What the browser sees AFTER (final result):**

```html
<header>
  <nav>
    <a href="/">Home</a>
    <a href="/about">About</a>
  </nav>
</header>
```

The `<div>` is **gone**. It's been replaced by the actual header content.

---

**So the flow is:**

```
Your HTML file          →  empty placeholder
       ↓
JS fetches the partial  →  downloads the file
       ↓
JS replaces placeholder →  pastes the partial's content in its place
       ↓
Browser renders         →  looks like you wrote it inline
```

**The key idea:** `data-include` is just a **marker** — a flag that says *"hey JS, go fetch this file and put it here."* The `data-` prefix is a standard HTML convention for custom attributes that the browser ignores but your JS can read.

It's the same concept as Pug's `include header` — the difference is just *when* it happens:
- **Pug**: at **build time** (compiler does it before the browser ever sees the file)
- **`data-include`**: at **runtime** (browser loads the page, then JS fetches and injects)

That's the trade-off — no build step, but a tiny delay while `fetch` loads the partial.

## `main.js` — the orchestrator

```js
// main.js — single entry point, orchestrates everything

// ─── 1. Load static partials (header, footer) ───────────────────
async function loadIncludes() {
  const els = document.querySelectorAll('[data-include]');
  await Promise.all(
    [...els].map(async el => {
      const res = await fetch(el.dataset.include);
      el.outerHTML = await res.text();
    })
  );
}

// ─── 2. Load dynamic data (JSON) ───────────────────────────────
async function loadData() {
  const res = await fetch('data/content.json');
  return res.json();
}

// ─── 3. Load markdown content ──────────────────────────────────
async function loadMarkdown(path) {
  const res = await fetch(path);
  const text = await res.text();
  return marked.parse(text); // returns HTML string
}

// ─── 4. Render components with data ────────────────────────────
function renderHero(data) {
  const el = document.getElementById('hero');
  el.innerHTML = `
    <h1>${data.hero.title}</h1>
    <p class="subtitle">${data.hero.subtitle}</p>
  `;
}

function renderCards(data) {
  const el = document.getElementById('cards');
  el.innerHTML = '';
  data.cards.forEach(card => {
    const cardEl = document.createElement('my-card');
    cardEl.setAttribute('title', card.title);
    cardEl.setAttribute('body', card.body);
    cardEl.setAttribute('tag', card.tag);
    el.appendChild(cardEl);
  });
}

async function renderContent(data) {
  const el = document.getElementById('content');
  const html = await loadMarkdown(data.contentFile);
  el.innerHTML = html;
}

// ─── 5. Boot ───────────────────────────────────────────────────
async function init() {
  await loadIncludes();
  const data = await loadData();

  renderHero(data);
  renderCards(data);
  await renderContent(data);

  console.log('✅ App ready');
}

init();
```

## `components/my-card.js` — web component with state

This is where **state management** comes in. The pattern for web components:

```js
// components/my-card.js

class MyCard extends HTMLElement {

  // ─── Observed attributes (external state) ─────────────────
  static get observedAttributes() {
    return ['title', 'body', 'tag', 'expanded'];
  }

  // ─── Internal state (private) ────────────────────────────
  #expanded = false;
  #likes = 0;

  // ─── React to attribute changes from outside ─────────────
  attributeChangedCallback(name, oldValue, newValue) {
    if (oldValue !== newValue) {
      this.render();
    }
  }

  // ─── Lifecycle ───────────────────────────────────────────
  connectedCallback() {
    this.render();
  }

  // ─── Public API (other scripts can call these) ───────────
  toggle() {
    this.#expanded = !this.#expanded;
    this.render();
    // Notify parent if needed:
    this.dispatchEvent(new CustomEvent('card-toggle', {
      detail: { expanded: this.#expanded, title: this.getAttribute('title') },
      bubbles: true
    }));
  }

  like() {
    this.#likes++;
    this.render();
  }

  // ─── Render (the "view") ─────────────────────────────────
  render() {
    const title = this.getAttribute('title') || '';
    const body  = this.getAttribute('body') || '';
    const tag   = this.getAttribute('tag') || '';

    this.innerHTML = `
      <div class="card ${this.#expanded ? 'expanded' : ''}">
        <span class="tag">${tag}</span>
        <h3>${title}</h3>
        <p>${body}</p>
        ${this.#expanded ? '<p class="extra">Extra details here...</p>' : ''}
        <div class="actions">
          <button data-action="toggle">Toggle</button>
          <button data-action="like">♥ ${this.#likes}</button>
        </div>
      </div>
    `;

    // Bind events (event delegation)
    this.querySelector('[data-action="toggle"]')?.addEventListener('click', () => this.toggle());
    this.querySelector('[data-action="like"]')?.addEventListener('click', () => this.like());
  }
}

customElements.define('my-card', MyCard);
```

---

## State management patterns for web components

| Pattern | When to use | How |
|---|---|---|
| **Private class fields** (`#state`) | Local UI state (expanded, likes, active tab) | `#expanded = false` |
| **`observedAttributes`** | External state passed as attributes | Parent sets `attr`, child re-renders |
| **Custom Events** (`bubbles: true`) | Child → parent communication | `dispatchEvent(new CustomEvent(...))` |
| **`<slot>`** | Parent provides content, child provides structure | `<my-card><p>custom</p></my-card>` |
| **Global store** (simple object) | Shared state across many components | See below |

### Simple global store (no library needed)

```js
// store.js
const store = {
  _state: {},
  _listeners: {},

  get(key) {
    return this._state[key];
  },

  set(key, value) {
    this._state[key] = value;
    (this._listeners[key] || []).forEach(fn => fn(value));
  },

  on(key, fn) {
    (this._listeners[key] ||= []).push(fn);
  }
};

// Usage in any component:
// store.set('theme', 'dark');
// store.on('theme', (val) => this.setAttribute('theme', val));
```

## 3. SEO / "Hydration"

You're mixing up two concepts:

| Term | What it means | Applies to you? |
|---|---|---|
| **Hydration** | React/Vue/Svelte: server renders HTML, then JS "attaches" behavior to existing DOM | ❌ Not applicable — you're not using a framework |
| **SEO for dynamic content** | Making sure Google can see your content | ⚠️ Yes, this matters |

**The problem:** Your cards and markdown content are injected by JS. A basic crawler (or a user with JS disabled) sees empty `<section>` tags.

**Solutions (simplest → most complex):**

| Approach | How |
|---|---|
| **Pre-render critical content** | Put the hero title + first card directly in `index.html` as static HTML. Only load *additional* cards via JS. |
| **SSR with a tiny server** | Use Express to render the final HTML server-side (like EJS does). The browser gets complete HTML, no JS needed for content. |
| **Prerender / SSG** | Build step that generates static `.html` files from your JSON/MD (this is what **Eleventy** or **Astro** do). |
| **`<noscript>` fallback** | Minimum: add a `<noscript>` tag with the key content for crawlers that don't execute JS. |

**For your project, the pragmatic fix:**

```html

## 4. What is `store.js` and who calls it?

It's a **tiny pub/sub (publish/subscribe) system** — a way for components to share state without a framework.

**Who calls it:** *You* do, in your components. Example:

```js
// components/my-nav.js
import { store } from '../store.js';

class MyNav extends HTMLElement {
  connectedCallback() {
    // Subscribe: "whenever 'theme' changes, update my class"
    store.on('theme', (val) => {
      this.classList.toggle('dark', val === 'dark');
    });

    // Read current value
    const current = store.get('theme');
    if (current === 'dark') this.classList.add('dark');
  }
}
```

```js
// main.js — somewhere a user clicks "toggle theme"
import { store } from './store.js';

document.getElementById('theme-toggle').addEventListener('click', () => {
  const next = store.get('theme') === 'dark' ? 'light' : 'dark';
  store.set('theme', next);  // ← all subscribed components update
});
```

**In short:** it's a 10-line replacement for Redux/Context/Signal. You only need it when **multiple components** need to react to the **same piece of state** (theme, user, cart, etc.). For your current project (cards + markdown), you **don't need it yet** — it's there for when you add interactivity like a theme toggle or a live search filter.

## Pub/Sub — from zero

### Real-world analogy

Think of a **newspaper subscription**:

- You **subscribe** to a newspaper (you "listen" for updates)
- The publisher **publishes** a new issue (sends the update)
- You get it **automatically** without asking every morning

You don't call the newspaper every day to check. You just said "send me the next one" once, and it arrives.

That's pub/sub. **One thing publishes, many things subscribe, and they react automatically.**

---

### Step 1 — The simplest possible example

Open a blank HTML file. No components, no fetch, nothing. Just this:

```html
<!DOCTYPE html>
<html>
<body>
  <h1>Pub/Sub Demo</h1>
  <button id="btn">Click me</button>
  <p id="out"></p>

  <script type="module">
    // ─── THE "STORE" (the newspaper office) ───────────────
    const listeners = [];

    // "Subscribe" — register a function to be called
    function on(fn) {
      listeners.push(fn);
    }

    // "Publish" — call all registered functions with a value
    function publish(value) {
      listeners.forEach(fn => fn(value));
    }

    // ─── "SUBSCRIBERS" (people who want the newspaper) ───

    on((msg) => {
      document.getElementById('out').textContent = msg;
      console.log('Subscriber A got:', msg);
    });

    on((msg) => {
      console.log('Subscriber B got:', msg);
    });

    // ─── "PUBLISHER" (the button) ──────────────────────────
    document.getElementById('btn').addEventListener('click', () => {
      publish('Hello! It works!');
    });
  </script>
</body>
</html>
```

**Click the button.** Both subscribers fire. Open DevTools console — you'll see both messages.

That's the entire pattern. 10 lines of "store", 6 lines of subscribers, 2 lines of publisher.

---

### Step 2 — Why do you need this?

**Without pub/sub**, if you have two components that need to react to the same thing:

```js
// Component A
function componentA() {
  // ... 50 lines of code ...
  // When user clicks "dark mode", I need to update myself
  document.getElementById('theme-btn').addEventListener('click', () => {
    this.classList.add('dark');
  });
}

// Component B
function componentB() {
  // ... 50 lines of code ...
  // When user clicks "dark mode", I ALSO need to update myself
  document.getElementById('theme-btn').addEventListener('click', () => {
    this.classList.add('dark');
  });
}
```

Now add Component C, D, E... You're wiring each one **manually** to the same button. Messy.

**With pub/sub:**

```js
// Component A
function componentA() {
  store.on('theme', (val) => this.classList.toggle('dark', val === 'dark'));
}

// Component B
function componentB() {
  store.on('theme', (val) => this.classList.toggle('dark', val === 'dark'));
}

// Component C
function componentC() {
  store.on('theme', (val) => this.style.background = val === 'dark' ? '#111' : '#fff');
}

// The button (only ONE place publishes)
document.getElementById('theme-btn').addEventListener('click', () => {
  store.set('theme', store.get('theme') === 'dark' ? 'light' : 'dark');
});
```

Each component **doesn't know about the others**. They just say "tell me when theme changes." The button says "theme changed." Done.

### Step 3 — The store with keys (what you already have)

The `store.js` you have is just the Step 1 example, but organized **by key** so you can track multiple things:

```js
// store.js
const store = {
  _state: {},        // { theme: 'dark', user: 'bob', cart: 3 }
  _listeners: {},    // { theme: [fn1, fn2], user: [fn3] }

  get(key) {
    return this._state[key];
  },

  set(key, value) {
    this._state[key] = value;
    (this._listeners[key] || []).forEach(fn => fn(value));
  },

  on(key, fn) {
    (this._listeners[key] ||= []).push(fn);
  }
};

export { store };
```

**`on('theme', fn)`** → "call `fn` whenever `theme` changes"
**`set('theme', 'dark')`** → "theme is now 'dark', notify everyone who cares"
**`get('theme')`** → "what's the current value?"

## Step 1 — Graceful fetch errors

The problem: if a file is missing or the server is down, your page **silently breaks** (or throws an uncaught error).

```js
// ❌ Before — one missing file kills everything
async function include(id, path) {
  const el = document.getElementById(id);
  const res = await fetch(path);
  el.innerHTML = await res.text();
}
```

```js
// ✅ After — each include is independent, errors are visible
async function include(id, path) {
  const el = document.getElementById(id);
  try {
    const res = await fetch(path);
    if (!res.ok) throw new Error(`${res.status} ${res.statusText}`);
    el.innerHTML = await res.text();
  } catch (err) {
    el.innerHTML = `
      <div style="background:#fee; border:1px solid #fcc; padding:0.5rem; color:#a00;">
        ⚠️ Failed to load <code>${path}</code>: ${err.message}
      </div>
    `;
    console.error(`[include] ${path}`, err);
  }
}
```

**Key rules:**
- `try/catch` **per fetch** (not one big try around everything)
- Check `res.ok` (fetch doesn't throw on 404/500 — it only throws on network failure)
- Show the error **in the DOM** (so you see it while developing)
- One partial failing **doesn't kill the others**

function updateCard(id, newData) {
  const el = document.querySelector(`[data-card-id="${id}"]`);
  if (!el) return;

  // Update only the parts that changed
  if (newData.title !== undefined) {
    el.querySelector('h3').textContent = newData.title;
  }
  if (newData.body !== undefined) {
    el.querySelector('p').textContent = newData.body;

**The pattern:**

| Action | Method |
|---|---|
| Add one item | `el.appendChild(newNode)` |
| Remove one item | `node.remove()` |
| Change text in one item | `el.querySelector('h3').textContent = '...'` |
| Change a class | `el.classList.add('active')` |
| Rebuild everything (last resort) | `el.innerHTML = ...` |

**Rule of thumb:** if you can target one element, don't wipe the container.

## 1. Latency — the "flash of empty page"

**The problem:** Your page loads → browser sees empty `<div>`s → JS runs → `fetch` fires → 50–300ms later content appears. User sees a blank flash.

**Solutions (simplest → best):**

### A. Skeleton placeholders (instant visual feedback)

```html
<div id="slot-header" style="min-height:60px; background:#f0f0f0; border-radius:4px;"></div>
```

The div isn't empty — it has a **grey block** the user sees immediately. When the fetch finishes, it gets replaced. No "flash of nothing."

### B. Priority: load critical first, defer the rest

```js
// main.js
async function init() {
  // CRITICAL — load first (header, hero, first cards)
  await renderChrome();
  await renderCards();

  // NON-CRITICAL — load when browser is idle
  requestIdleCallback(async () => {
    await renderContent();   // markdown "about" section
    await loadAnalytics();   // any tracking scripts
    await loadRelatedPosts();// extra content below the fold
  });
}
```

`requestIdleCallback` = "run this when the browser has nothing else to do." If the browser is busy painting, it waits.

### C. `IntersectionObserver` — load when visible

```js
function lazyLoad(selector, path) {
  const el = document.querySelector(selector);
  const observer = new IntersectionObserver((entries) => {
    if (entries[0].isIntersecting) {
      fetch(path).then(r => r.text()).then(html => {
        el.innerHTML = html;
      });
      observer.disconnect(); // only load once
    }
  }, { rootMargin: '200px' }); // start loading 200px before visible

  observer.observe(el);
}

// Usage:
lazyLoad('#slot-related', 'partials/related.html');
lazyLoad('#slot-comments', 'partials/comments.html');
```

The browser **doesn't fetch** until the user scrolls near that section. Zero wasted bandwidth.

## 4. Relative paths in partials

**The problem:** `fetch('partials/header.html')` is relative to **the page URL**, not to the file that contains the `fetch` call.

If your page is at `/about.html`, then `fetch('partials/header.html')` looks for `/partials/header.html` ✓.

But if your page is at `/blog/post1.html`, it looks for `/blog/partials/header.html` ✗.

**Solutions:**

### A. Always use root-relative paths (simplest)
```js
// Always start with / — relative to the server root
await include('slot-header', '/partials/header.html');
await include('slot-footer', '/partials/footer.html');
```

Works as long as your site is at the domain root.

### B. Compute a base path (works in subdirectories)
```js
// In lib/home.js
const BASE = window.location.pathname.replace(/[^/]*$/, '');
// If page is /blog/post1.html → BASE = "/blog/"
// If page is / → BASE = "/"

export function resolve(path) {
  if (path.startsWith('/')) return path;  // already absolute
  return BASE + path;
}

// Usage:
await include('slot-header', resolve('partials/header.html'));
// → fetch('/blog/partials/header.html')
```

### C. Define a manifest (most robust)
```js
// lib/paths.js
export const ASSETS = {
  header:   '/partials/header.html',
  footer:   '/partials/footer.html',
  related:  '/partials/related.html',
  siteJson: '/data/site.json',
  aboutMd:  '/content/about.md',
};
```
```js
import { ASSETS } from './lib/paths.js';
await include('slot-header', ASSETS.header);
```

One place to change all paths. No scattering of strings.

## 5. Why the `marked` CDN? Can we do it without?

**What that line actually does:**
```html
<script src="https://cdn.jsdelivr.net/npm/marked/marked.min.js"></script>
```

It downloads a **`.js` file** from a server on the internet (jsdelivr is a CDN — a content delivery network that hosts npm packages). After it loads, `marked` becomes a global variable you can call: `marked.parse(text)`.

**You do NOT need a CDN.** Three options:

### Option A: Download it locally (recommended)
```bash
npm install marked
# or just download the file:
curl -o libs/marked.min.js https://cdn.jsdelivr.net/npm/marked/marked.min.js
```
```html
<script src="libs/marked.min.js"></script>
```
Same thing, but the file is **in your project**. No internet dependency.

### Option B: Use ES module import (cleaner)
```js
// main.js
import { marked } from './libs/marked.esm.js';

const html = marked.parse(text);
```

### Option C: Write your own (what I did in `lib/home.js`)

The `md()` function in the "Home Framework" above is a **15-line regex-based markdown parser**. It handles:
- `# headings`
- `**bold**`, `*italic*`
- `` `code` ``
- `> blockquotes`
- `- lists`
- `[links](url)`

It's not a full CommonMark implementation, but for basic content (headings, bold, lists, links) it's **zero dependencies, zero network requests, zero build step**.

**When to use which:**

| Your markdown complexity | Use |
|---|---|
| Headings, bold, italic, links, lists | Your own `md()` (15 lines) |
| Tables, code blocks with syntax highlighting, nested lists | `marked` locally (Option A/B) |
| Full CommonMark + extensions | `marked` or `markdown-it` |

## 6. How calling a library works

**A library is just a `.js` file.** That's it. No magic.

```
libs/
└── marked.min.js    ← 23KB of JavaScript code
```

When you write:
```html
<script src="libs/marked.min.js"></script>
```

The browser **downloads that file and runs it**. The file contains something like:
```js
// (simplified — the real file is 23KB)
function parse(text) { /* ... converts markdown to html ... */ }
function use(options) { /* ... */ }
window.marked = { parse, use };  // ← makes itself available globally
```

After that line executes, `window.marked.parse("**hi**")` returns `<p><strong>hi</strong></p>`.

**With ES modules** (your case):
```js
// libs/marked.esm.js (end of the file)
export { parse as marked };
```
```js
// main.js
import { marked } from './libs/marked.esm.js';
```

**The CDN version is the same file**, just hosted on a public server instead of your own. The only difference:

| | Local file | CDN |
|---|---|---|
| Where the .js lives | Your project folder | Someone else's server |
| Needs internet? | No (it's on disk) | Yes (browser fetches it) |
| Version control | You pin it | They might update/break it |
| Offline? | Works | Broken |

**For a personal project: always use local files.** No reason to depend on a third-party server.

## The golden rule that fixes 90% of these messes

**Everything that touches the DOM goes inside `init()`.** Top-level `await` in a module runs *before* the DOM is fully parsed in some edge cases, and it scatters logic everywhere. One `init()` function, called once at the bottom, is your single entry point.

```
imports (top)
functions (middle)
init() call (bottom)
```

Nothing else at the top level. That's it.

## 1. Nested subdirectories — the real problem

Your current `resolve()` breaks when you have pages at different depths that share partials:

```
/my-site/
├── index.html              ← BASE = "/"
├── blog/
│   ├── post1.html          ← BASE = "/blog/"
│   └── post2.html
└── about/
    └── team.html           ← BASE = "/about/"
```

If `partials/` lives at the **root**, `resolve('partials/header.html')` from `/blog/post1.html` looks for `/blog/partials/header.html` — wrong.

### Fix: define a root path explicitly

```js
// lib/home.js

// Option A: hardcode the site root (simplest, works for 99% of cases)
const ROOT = '/';  // or '/my-site/' if deployed in a subfolder

function resolve(path) {
  if (path.startsWith('/')) return path;
  return ROOT + path;
}
```

Now `resolve('partials/header.html')` always gives `/partials/header.html` regardless of where the page lives.

### Option B: auto-detect (if you can't hardcode)

```js
// Walk up until you find a known file
async function detectRoot() {
  const segments = window.location.pathname.split('/');
  for (let i = segments.length; i >= 0; i--) {
    const candidate = segments.slice(0, i).join('/') + '/';
    try {
      const res = await fetch(candidate + 'data/site.json', { method: 'HEAD' });
      if (res.ok) return candidate || '/';
    } catch { /* keep walking */ }
    if (candidate === '/') break;
  }
  return '/';
}

let ROOT = '/';
async function init() {
  ROOT = await detectRoot();
  // ... rest of init
}
```

This does 1–3 extra `HEAD` requests (tiny, no body) at startup. Overkill for a personal site — **Option A is fine**.

## 2. Optimized markdown parser

Your current `md()` runs **12 regex passes** over the entire string. For short content (< 5KB) that's fine. For longer docs, here's a faster approach:

### Strategy: split → parse per block → join

```js
// lib/home.js — optimized md()

function md(text) {
  // Split into blocks by double newline (paragraphs, headings, etc.)
  const blocks = text.split(/\n\n+/);

  const html = blocks.map(block => {
    const trimmed = block.trim();

    // Headings (check first — they're single lines)
    if (/^### /.test(trimmed)) return `<h3>${trimmed.slice(4)}</h3>`;
    if (/^## /.test(trimmed))  return `<h2>${trimmed.slice(3)}</h2>`;
    if (/^# /.test(trimmed))   return `<h1>${trimmed.slice(2)}</h1>`;

    // Blockquote
    if (/^> /.test(trimmed)) {
      const inner = trimmed.replace(/^> /gm, '');
      return `<blockquote>${inline(inner)}</blockquote>`;
    }

    // Unordered list
    if (/^- /.test(trimmed)) {
      const items = trimmed.split('\n').map(l => `<li>${inline(l.slice(2))}</li>`).join('');
      return `<ul>${items}</ul>`;
    }

    // Code block (``` ```)
    if (trimmed.startsWith('```')) {
      const lines = trimmed.split('\n').slice(1);
      const last = lines.findIndex(l => l === '```');
      if (last !== -1) lines.length = last;
      return `<pre><code>${lines.join('\n')}</code></pre>`;
    }

    // Regular paragraph
    return `<p>${inline(trimmed)}</p>`;
  }).join('');

  return html;
}

// Inline formatting (bold, italic, code, links) — applied per block, not whole doc
function inline(text) {
  return text
    .replace(/`([^`]+)`/g, '<code>$1</code>')
    .replace(/\*\*([^*]+)\*\*/g, '<strong>$1</strong>')
    .replace(/\*([^*]+)\*/g, '<em>$1</em>')
    .replace(/\[([^\]]+)\]\(([^)]+)\)/g, '<a href="$2">$1</a>');
}
```

**Why it's faster:**
- Inline regexes run on **small blocks** (one paragraph), not the whole document
- No global flag (`/gm`) — each block is one line or a short list
- Early return on headings (no regex scanning needed)

For a 10KB article, this is roughly **3–5× faster** than 12 global passes.

## 3. Nested lists + code blocks in `md()`

Your current parser only handles one level of `- `. Here's the upgraded version:

```js
// lib/home.js — replace md() and inline() with these

function md(text) {
  const blocks = text.split(/\n\n+/);

  const html = blocks.map(block => {
    const trimmed = block.trim();

    // Headings
    if (/^### /.test(trimmed)) return `<h3 class="md-h3">${trimmed.slice(4)}</h3>`;
    if (/^## /.test(trimmed))  return `<h2 class="md-h2">${trimmed.slice(3)}</h2>`;
    if (/^# /.test(trimmed))   return `<h1 class="md-h1">${trimmed.slice(2)}</h1>`;

    // Code block (``` ```)
    if (trimmed.startsWith('```')) {
      const lines = trimmed.split('\n');
      const lang = lines[0].slice(3).trim(); // e.g. "js", "python"
      const code = lines.slice(1).join('\n')
        .replace(/```$/g, '')  // remove closing ```
        .replace(/</g, '&lt;')
        .replace(/>/g, '&gt;'); // escape HTML
      const langClass = lang ? ` class="code--${lang}"` : '';
      return `<pre class="code-block"><code${langClass}>${code}</code></pre>`;
    }

    // Blockquote
    if (/^> /.test(trimmed)) {
      const inner = trimmed.replace(/^> /gm, '');
      return `<blockquote class="md-quote">${inline(inner)}</blockquote>`;
    }

    // List (handles nesting via indentation)
    if (/^- /.test(trimmed) || /^\s+- /.test(trimmed)) {
      return parseList(trimmed);
    }

    // Regular paragraph
    return `<p class="md-p">${inline(trimmed)}</p>`;
  }).join('');

  return html;
}

// ─── Nested list parser ────────────────────────────────────
function parseList(block) {
  const lines = block.split('\n');
  let html = '';
  let stack = []; // tracks indentation levels

  for (const line of lines) {
    // Count leading spaces (2 spaces = 1 level)
    const match = line.match(/^(\s*)- (.*)/);
    if (!match) continue;

    const indent = Math.floor(match[1].length / 2);
    const content = inline(match[2]);

    // Close any open <ul> that's deeper than current level
    while (stack.length > indent + 1) {
      html += '</li></ul>';
      stack.pop();
    }

    // Open new <ul> if we're going deeper
    if (stack.length < indent + 1) {
      html += '<ul>';
      stack.push(indent);
    } else {
      html += '</li>';
    }

    html += `<li>${content}`;
  }

  // Close all remaining open tags
  while (stack.length > 0) {
    html += '</li></ul>';
    stack.pop();
  }

  return html;
}

// ─── Inline formatting ─────────────────────────────────────
function inline(text) {
  return text
    .replace(/`([^`]+)`/g, '<code class="md-code">$1</code>')
    .replace(/\*\*([^*]+)\*\*/g, '<strong>$1</strong>')
    .replace(/\*([^*]+)\*/g, '<em>$1</em>')
    .replace(/\[([^\]]+)\]\(([^)]+)\)/g, '<a href="$2" class="md-link">$1</a>');
}
```

// ─── Theme ─────────────────────────────────────────────────

function getCookie(name) {
  const match = document.cookie.match(new RegExp(`(^| )${name}=([^;]+)`));
  return match ? match[2] : null;
}

function setCookie(name, value, days) {
  const d = new Date();
  d.setTime(d.getTime() + days * 24 * 60 * 60 * 1000);
  document.cookie = `${name}=${value};expires=${d.toUTCString()};path=/`;
}

function initTheme() {
  // 1. Priority: cookie > system preference
  const saved = getCookie('theme');
  const systemDark = window.matchMedia('(prefers-color-scheme: dark)').matches;
  const isDark = saved ? saved === 'dark' : systemDark;

  applyTheme(isDark);

  // 2. Listen for system changes (only if no cookie set)
  if (!saved) {
    window.matchMedia('(prefers-color-scheme: dark)')
      .addEventListener('change', (e) => applyTheme(e.matches));
  }

  // 3. Wire the button
  const btn = document.getElementById('theme-toggle');
  if (btn) {
    btn.addEventListener('click', () => {
      const isDark = document.documentElement.classList.toggle('dark');
      setCookie('theme', isDark ? 'dark' : 'light', 365); // 1 year
      updateThemeIcon(isDark);
    });
  }
}

function applyTheme(isDark) {
  document.documentElement.classList.toggle('dark', isDark);
  updateThemeIcon(isDark);
}

function updateThemeIcon(isDark) {
  const btn = document.getElementById('theme-toggle');
  if (btn) btn.textContent = isDark ? '☀️' : '🌙';
}
```

**Why cookies over `localStorage`:**
- Cookies are sent to the server (useful if you later add SSR and want the server to render the right theme)
- `localStorage` is client-only
- For a purely client-side project either works, but cookies are more "web-standard" for preferences

## "Is this how developers create web pages nowadays?"

**Short answer: no.** Here's the honest landscape:

| Approach | Who uses it | What it is |
|---|---|---|
| **React / Next.js** | Most startups, big companies | JS framework, virtual DOM, component-based |
| **Vue / Nuxt** | European companies, smaller teams | Similar to React but simpler |
| **Svelte / SvelteKit** | Growing fast | Compiles to vanilla JS, no runtime |
| **Astro** | Content sites, blogs | "Islands" architecture, ships zero JS by default |
| **Eleventy (11ty)** | Static sites, docs | Template engine + SSG, no JS framework |
| **What you built** | Personal projects, learning | Vanilla JS micro-framework |

**What you built is valid** — it's essentially a hand-rolled Eleventy. But the industry moved to frameworks because:

1. **Component state** — React/Vue handle re-rendering, props, lifecycle automatically. Your `updateCard()` is manual.
2. **Routing** — Next.js/Astro give you file-based routing for free. You'd have to write a router.
3. **Build tooling** — Vite, webpack, HMR (hot reload), tree-shaking, minification.
4. **Ecosystem** — 10,000+ packages vs. your 60-line `home.js`.

**Where your approach wins:**
- Zero dependencies, zero build step
- You understand every line
- Tiny bundle (your whole "framework" is ~2KB)
- No framework lock-in

**Where it breaks down:**
- Complex state (forms, auth, real-time updates)
- Large teams (no conventions, no tooling)
- SEO (you're rendering client-side — Google has to execute JS)

**The realistic path for you:** what you've learned (modular HTML, fetch, components, state) transfers **directly** to Svelte or Astro. You'll recognize every concept. The frameworks just automate the tedious parts you're doing by hand.

Your "Home Framework" is a great **learning tool**. For a real production site, I'd suggest trying **Astro** next — it's the closest to what you've built (content-first, partials, minimal JS) but with a build step, SSR option, and proper routing.

function md(text) {
  const blocks = text.split(/\n\n+/);
  return blocks.map((block) => {
    const trimmed = block.trim();

    if (/^### /.test(trimmed)) return `<h3 class="md-h3">${trimmed.slice(4)}</h3>`;
    if (/^## /.test(trimmed))  return `<h2 class="md-h2">${trimmed.slice(3)}</h2>`;
    if (/^# /.test(trimmed))   return `<h1 class="md-h1">${trimmed.slice(2)}</h1>`;

    if (trimmed.startsWith("```")) {
      const lines = trimmed.split("\n");
      const lang = lines[0].slice(3).trim();
      const code = lines.slice(1).join("\n")
        .replace(/```$/g, "")
        .replace(/</g, "&lt;")
        .replace(/>/g, "&gt;");
      const langClass = lang ? ` class="code--${lang}"` : "";
      return `<pre class="code-block"><code${langClass}>${code}</code></pre>`;
    }

    if (/^(-{3,}|\*{3,}|_{3,})$/.test(trimmed)) return `<hr class="md-hr">`;

    if (/^> /.test(trimmed)) {
      const inner = trimmed.replace(/^> /gm, "");
      return `<blockquote class="md-quote">${inline(inner)}</blockquote>`;

function parseList(block) {
  const lines = block.split("\n");
  let html = "";
  let stack = [];

  for (const line of lines) {
    const match = line.match(/^(\s*)- (.*)/);
    if (!match) continue;
    const indent = Math.floor(match[1].length / 2);
    const content = inline(match[2]);

    while (stack.length > indent + 1) { html += "</li></ul>"; stack.pop(); }
    if (stack.length < indent + 1) { html += "<ul>"; stack.push(indent); }
    else { html += "</li>"; }
    html += `<li>${content}`;
  }
  while (stack.length > 0) { html += "</li></ul>"; stack.pop(); }
  return html;
}

If that works → your `detectRoot()` or `resolve()` had a path issue. If it still 404s → the file genuinely isn't at `/data/site.json` on the server, and you need to check your folder structure and where you're running `npx serve .` from.

Here's the algorithm, step by step:

```js
async function detectRoot() {
  const segments = window.location.pathname.split("/");
  // If page is /index4 → segments = ["", "index4"]
  // If page is /blog/post1.html → segments = ["", "blog", "post1.html"]

  for (let i = segments.length; i >= 0; i--) {
    // Build candidate paths, walking UP from the current page:
    //
    // i = 2: "" + "/" = "/"
    // i = 1: "/index4" + "/" = "/index4/"
    // i = 0: "" + "/" = "/"
    //
    // For /blog/post1.html:
    // i = 3: "/"
    // i = 2: "/blog/"
    // i = 1: "/"
    // i = 0: "/"

    const candidate = segments.slice(0, i).join("/") + "/";

    try {
      // Try to HEAD-request a known file at this level
      const res = await fetch(candidate + "data/site.json", { method: "HEAD" });
      if (res.ok) {
        ROOT = candidate || "/";  // Found it! Stop.
        return;
      }
    } catch { /* network error, keep walking up */ }

    if (candidate === "/") break;  // Already at the top, stop
  }

  ROOT = "/";  // Fallback: assume root
}
```

**The logic:**

1. **Start at the current page's directory** (deepest level)
2. **Walk up one level at a time** (like `cd ..`)
3. **At each level**, try `HEAD` on a **known file** (`data/site.json`)
4. **First level where the file exists** = your site root
5. **If nothing found** → default to `/`

**Concrete example:**

Your page is at `/index4`, your files are at the server root:

```
Server root/
├── data/
│   └── site.json      ← this is where the file actually is
├── partials/
├── index.html
└── index4.html        ← you're here
```

```
Attempt 1: HEAD /index4/data/site.json  → 404 ✗ (no data/ inside index4)
Attempt 2: HEAD /data/site.json         → 200 ✓ → ROOT = "/"
```

**Why `HEAD` instead of `GET`:**
- `HEAD` sends only the **headers** (no body) — much smaller request
- You only care about the **status code** (200 = exists, 404 = not here)
- Faster, less bandwidth

**The problem you hit:**

Your page was at `/index4`, so the first attempt was `/index4/data/site.json` → 404. The second attempt `/data/site.json` should have worked **if** you're running `npx serve .` from the correct folder (the one containing `data/`). If that also 404'd, the server root wasn't where you expected.

**The simpler alternative** (what I recommended): just hardcode it:

```js
let ROOT = "/";  // Done. No probing, no extra requests.
```

`detectRoot()` is useful when you **don't know** where your site will be deployed (e.g., a GitHub Pages subfolder like `/my-repo/`). For a local project you control, hardcoding is fine.
